# Array Animation — Excellence Spec

This is the target document Phases 3-6 of the array redesign are measured against. It defines what "good" means concretely — named techniques, how each maps to AQVL's actual array operations (INSERT, DELETE, UPDATE, SWAP, COMPARE, HIGHLIGHT), what makes sorting algorithms recognizable by eye, how to communicate *why* not just *that*, and an observable pass/fail checklist. It does not describe implementation (no anime.js configs, no component names) — that's for the redesign phases. It draws on the gaps documented in `array-current-state-audit.md`, referenced throughout as "current:" callouts so the spec stays anchored to the real baseline instead of a hypothetical one.

---

## 1. Techniques

### 1.1 Weight and anticipation (motion has physical presence)

Real objects don't teleport, and they don't move at constant velocity either — they wind up before a big action and settle after it. This is Disney animation's "anticipation" and "follow-through/overshoot" principles applied to data: a small backward/inward motion before the real motion telegraphs "something is about to happen here," and a small overshoot-and-settle after arrival telegraphs "it has arrived and is now at rest," rather than the motion simply stopping. The absence of both is what makes motion read as "mechanical" — an object that accelerates instantly, moves at constant speed, and stops instantly has no weight.

**Applied to array operations:**
- **SWAP**: the two elements should lift and load (a brief upward/backward pre-motion) before crossing paths, cross at different depths so their paths don't visually intersect (avoiding an ambiguous "did they pass through each other" moment), and land with a slight overshoot-and-bounce rather than stopping dead in the new slot. *Current: the direct-`SWAP` path already does lift+arc+bounce (~1750ms); the builtin-sort SWAP path does a flat, no-lift, no-bounce tween (~1000ms) for the identical logical operation — this is the single clearest violation of "same operation, same physical presence" in the current system and should be the first thing unified.*
- **INSERT**: the incoming element should have a point of origin the viewer can track (not spawn from an arbitrary off-screen coordinate with no visual link to the insertion call) and should settle with a bounce, signaling "newly arrived and still slightly unsettled" rather than snapping into full size instantly. *Current: element spawns at a fixed off-scene point unrelated to any on-screen source and pops in at 500-600ms — the bounce-in exists but the point of origin carries no meaning.*
- **DELETE**: the outgoing element should shrink/fade with an accelerating (not linear) motion — objects that are "falling away" or "dissolving" speed up, they don't move at constant velocity — and neighboring elements closing the gap should have their own small settle-bounce on arrival, not just glide to a stop.
- **UPDATE**: a value change in place should still carry a tiny anticipation flinch before the new value appears — even though nothing moves in space, a value-only change benefits from a compress-then-expand "impact" pulse rather than a pulse that starts immediately at full amplitude.
- **COMPARE**: the pre-comparison lift should read as a genuine "leaning in to look," meaning it should be slower to rise than to fall (asymmetric timing), because attention-gathering motions in nature ease in slowly and release quickly.

### 1.2 A real color/emphasis vocabulary (state, not just on/off)

The failure mode to avoid is a system with exactly two states — "highlighted" and "not" — applied uniformly regardless of what the highlight means. A real vocabulary assigns each color to exactly one semantic meaning, and different meanings never share a color, so the color alone (without reading any text) tells the viewer what kind of thing is happening. A viable minimum vocabulary for array operations:

| Color role | Meaning | Should NOT also mean |
|---|---|---|
| Neutral/gray | Untouched, not yet part of the current operation | anything else |
| Amber/yellow | Currently being examined/compared (outcome not yet decided) | a mutation has happened |
| Red/orange | Decided — about to move, be overwritten, or be removed | merely being looked at |
| Blue/violet (in transit) | Actively moving/mutating right now | a static/idle state |
| Green | Confirmed correct / settled into final position / operation complete | still subject to change |

**Applied to array operations:**
- **COMPARE**: amber during evaluation. The instant the comparison *resolves*, the color should diverge based on outcome — e.g., the element that "wins" (will move, or is not swapped) can flash toward red/blue depending on what happens next, rather than both elements sharing one color throughout and the outcome existing only as console text. *Current: COMPARE is a single amber pulse with zero visual differentiation of `<` vs `>` vs `=` — the outcome is real data (already computed and logged) that never reaches the canvas.*
- **SWAP**: should use the "about to move" red/orange *before* the swap begins (shared with the decision that triggered it, e.g. a losing COMPARE), then transition to the "in transit" color during the actual position exchange — not the same static "modifying" color for the entire duration. *Current: INSERT, UPDATE, SWAP, PUSH, and POP all use one identical pink "MODIFYING" token for their entire duration — this is the current system's largest vocabulary collapse (see audit §6) and directly violates "different meanings never share a color."*
- **INSERT**: the incoming element can use the "in transit" color while entering and cross into neutral once settled — distinct from UPDATE's in-place pulse and SWAP's exchange, even though all three currently render identically.
- **DELETE**: could use the red "about to be removed" tone *before* shrinking starts (a beat of "this one is marked"), consistent with using red generally for "decided, about to be acted on."
- **Confirmed-sorted region** (see §3): green, applied cumulatively and left on — this is the one state in the vocabulary above that is explicitly persistent, everything else should resolve back to neutral once its moment passes.

### 1.3 Camera as attention director, not passive observer

A camera that shows the whole structure at a constant, unchanging framing forces the viewer to scan for what matters themselves — every frame demands equal visual attention, so nothing gets emphasis. A camera that reframes toward the *locus of decision* (where a comparison or swap is currently happening) does the viewer's attention-allocation for them, the way a documentary cut or a comic panel does.

**Applied to array operations:**
- During a COMPARE or SWAP involving two adjacent or nearby elements, the camera (or a local focus effect — e.g., depth-of-field falloff on non-participating elements, or a subtle push-in) should draw toward that pair rather than holding a static full-array framing throughout. *Current: `AUTO_FIT` recenters on the mean position and adjusts zoom only in response to the array's overall span — it does not react to which specific elements are currently active, so the camera behaves identically whether index 0 and 1 are being compared or index 40 and 41 are.*
- For operations happening in a spatially narrow region (e.g., a merge-sort comparing across two halves that are far apart), the camera should be willing to widen briefly to show *both* participants rather than snapping between them — cuts should be motivated by "the viewer needs to see this relationship," not just "an event fired."
- Camera should never move for its own sake — a swap two rows away from the current focus doesn't need a cut if it's not part of the narrative beat currently being told; over-eager camera movement is as bad as a static camera, since it produces seasickness instead of guidance.

### 1.4 Sound as a second, low-attention channel

Sound's advantage is that it can convey rhythm and outcome without competing for the eye's attention — a distinct comparison tick vs. a satisfying swap "clunk" vs. a rising confirmation chime lets a viewer *feel* the pace and success/failure of operations peripherally, reinforcing what they're already seeing rather than requiring them to read anything. The design risk is annoyance from repetition — audio must vary (pitch, velocity) with context or it becomes noise within seconds.

**Applied to array operations:** a short, pitched tick on COMPARE (pitch could rise/fall with the compared values, giving an auditory hint of magnitude before the visual outcome even resolves); a fuller two-part "swap" sound (two brief tones, one per element, panned to left/right matching their positions) on SWAP; a soft confirmation tone when an element joins the "confirmed sorted" region; near-silence or a single subtle tick for INSERT/DELETE/UPDATE since they're comparatively rare/important events that shouldn't compete with the constant comparison ticking. *Current (audit §4): zero sound exists anywhere in the codebase — this is a fully greenfield addition, not a fix.*

### 1.5 Variable pacing (rhythm tells you what matters)

Uniform-duration animations for every operation flatten importance — if a routine comparison and the pivotal deciding swap of the whole algorithm take exactly the same time, nothing feels pivotal. Real pacing compresses the obvious/repetitive and expands the decisive: many algorithms visualizers speed through a long run of "no swap needed" comparisons and visibly slow down for the comparison that finally triggers the swap, or for the merge step that finally interleaves two sorted halves.

**Applied to array operations:** comparisons that don't result in a swap can be faster and lower-amplitude (a quick flick) than comparisons that do (a fuller pulse-and-hold), because the *decision* is the interesting event, not the mere act of comparing. Early passes of an O(n²) sort (which are mostly "no, don't swap") can run faster than later passes where swaps are more consequential (e.g., the final few comparisons that lock in element positions). *Current: every COMPARE runs the identical ~1000ms sequence regardless of outcome or algorithmic significance, and every SWAP-via-sort runs the identical ~1000ms regardless of how many elements are left to sort — there is no notion of pacing tied to algorithmic progress.*

## 2. Algorithm distinguishability

The test: mute all on-screen text, remove any title/label, and ask "could a viewer who has seen these algorithms before, but doesn't know which one this is, correctly name it within 10-15 seconds purely from motion?" Distinguishability comes from **where activity is spatially concentrated** and **the rhythm of comparisons vs. swaps**, not from color alone (since the vocabulary in §1.2 should be shared across all algorithms — using the same meaning for the same color is a feature, not a bug to work around per-algorithm).

- **Adjacent-swap / comparison-heavy sorts (Bubble Sort, Cocktail Shaker Sort)**: activity is a single "wave" that sweeps linearly across the array, always comparing *neighbors*, with a visibly shrinking active region each pass (the tail end becomes "confirmed sorted" and stops participating). Signature: one comparison locus moving steadily in one direction, occasional swap ripples, and a "green frontier" that grows from one end. Rhythm: relentless, evenly paced, mechanical-feeling *by nature of the algorithm* (which is fine — the goal is for bubble sort to look tedious/exhaustive, because it is).
- **Selection-based sorts (Selection Sort)**: one persistent "candidate" marker holds at a fixed left boundary while a second cursor sweeps the *entire remaining unsorted region* looking for the minimum/maximum, then a single swap moves the found element back to the boundary. Signature: a full sweep of many comparisons with no swaps, followed by exactly one swap per pass, then the boundary advances by one — visually this should look like "search, search, search... one decisive move" repeated, distinct from bubble sort's "compare-and-maybe-swap" repeated at every step.
- **Insertion-based sorts (Insertion Sort)**: activity is concentrated at a shifting boundary between "sorted prefix" and "the rest," with a single element being walked backward through the sorted prefix (comparing and shifting) until it finds its place. Signature: short, localized backward-walking bursts of varying length (sometimes the new element barely moves, sometimes it walks far back), unlike bubble sort's constant-length forward wave — the *variable* burst length pass-to-pass is itself a distinguishing rhythm.
- **Divide-and-conquer sorts (Merge Sort, Quick Sort)**: activity is spatially segmented — multiple independent regions of the array are active simultaneously (recursive subdivisions), not a single sweeping locus. Merge Sort in particular should show two adjacent sorted sub-regions being interleaved with a visible "merge frontier" advancing through both simultaneously (two cursors converging into one output run), which looks structurally different from a single-cursor sweep. Quick Sort should show a *partition* signature: one "pivot" element held in place/highlighted distinctly while two cursors sweep from either end of a sub-region toward each other, swapping across the pivot boundary — then the pivot locks into its final spot (a confirmation beat) and the array visibly *splits* into two independently-active regions for the recursive calls. Signature for the whole family: simultaneous, spatially-separated pockets of activity rather than one continuous sweep, and a visible split/recursion moment.
- **Heap-based sorts (Heap Sort)**: if ever implemented, activity should reflect the tree-like parent/child comparison structure (comparisons jump between non-adjacent indices following the heap index formula) rather than sweeping neighbors — this alone (non-adjacent comparison jumps with no linear sweep pattern) is enough to distinguish it from every algorithm above.

**General rule for distinguishability**: the number of simultaneously-active regions, whether the active region shrinks/grows/splits, whether comparisons are always-adjacent or can jump, and whether swap frequency is constant or front-loaded/back-loaded are the four structural signals to preserve per-algorithm. Two algorithms that differ only in average number of swaps but share all four of those signals will *not* be visually distinguishable and that's an acceptable limit, not a failure — the goal is category-level distinguishability (comparison-sweep vs. selection vs. insertion-walk vs. divide-and-conquer), not distinguishing every algorithm from every other by animation alone.

## 3. The narrative layer (communicating WHY, not just THAT)

Three mechanisms, evaluated on cost (screen space, attention competition, implementation complexity) vs. benefit:

**A. On-screen contextual text, updated per step** (e.g., a persistent single-line caption: "comparing arr[2] and arr[3]"). *Benefit*: unambiguous, reuses existing `RUNTIME_LOG` text content (audit §7 confirms this text already exists and is already correctly worded — the gap is purely that it's rendered in a separate DOM console instead of composited near the canvas). *Cost*: requires a reading viewer, competes with the 3D scene for eye attention, and scales poorly if operations happen quickly (text becomes a scrolling blur). *Verdict*: valuable as a low-effort, high-clarity addition — but it should be treated as a *supplement* for viewers who want detail, not the primary communication channel, because a viewer who has to read to understand isn't actually watching an animation, they're reading a log with pictures.

**B. A visual "reason" indicator anchored between the participating elements** (e.g., a connecting line/arc drawn between two elements the instant a COMPARE begins, before any color change — visually saying "these two are now in a relationship" prior to the outcome). *Benefit*: spatially co-located with the action (no eye travel required, unlike A), works even at high speed since it's a shape not text, and naturally generalizes — an INSERT could show a faint line from the value's logical source to its destination, a SWAP's connecting line could bend/animate to show the exchange direction. *Cost*: needs a well-designed visual grammar so the indicator itself doesn't need a legend (e.g., a plain line = "comparing," an arrow = "moving toward," a broken/snapped line = "comparison resolved, decision made") — this requires more design iteration than text does, since text is self-explanatory and a novel line convention is not, on first viewing. *Verdict*: this is the technique most worth prioritizing for the primary channel, since it directly plugs the audit's most concrete narrative gap (COMPARE's outcome existing only as text, never on-canvas, audit §1 COMPARE.3) using a spatial rather than textual solution, and it composes with the color vocabulary in §1.2 rather than replacing it.

**C. A progress/confirmation indicator showing sorted vs. unsorted extent** (e.g., a persistent green "confirmed sorted" region marker, or a boundary line that advances as the algorithm progresses). *Benefit*: answers a different but equally important narrative question — not "why is this specific comparison happening" but "how close is this algorithm to done, and what does 'done' mean for this element." This is also what directly enables the algorithm-distinguishability signals in §2 (bubble sort's shrinking active region, insertion sort's growing sorted prefix, quick sort's splitting regions all *are* this indicator, applied per-algorithm). *Cost*: low — it's a derived/cumulative state, not a per-event decision, so it doesn't need to keep up with rapid per-comparison pacing the way A and B do. *Verdict*: should exist regardless of which of A/B is prioritized, because it's cheap and it's the mechanism that makes §2's algorithm signatures legible rather than merely present in the underlying motion.

**Recommendation for prioritization** (not a final decision — flagged for the redesign phase to confirm): B (spatial reason-indicator) as the primary in-scene narrative device since it fixes the biggest audited gap without requiring the viewer to read, C (progress/confirmation marker) as a persistent low-cost layer that also solves algorithm-distinguishability, and A (contextual caption text) retained as a supplementary detail channel for viewers who want it, ideally composited near the canvas rather than in a fully separate console component as it is today.

## 4. Success criteria (10-second, no-context observer test)

An outside observer, watching an AQVL array animation for 10 seconds with zero prior context (no title, no code visible), should be able to affirm all of the following for it to count as "well done." Each is written to be observable/falsifiable, not a vibe:

1. **They can name at least one thing currently happening** ("something is being compared," "an element is moving to a new spot") without having read any code — purely from watching. *Fails if*: highlighting looks like arbitrary color flicker with no inferable meaning.
2. **They can tell whether two simultaneously-colored elements mean the same thing or different things**, by color alone — e.g., they should not describe a swap and a value-update as "doing the same thing" if the two are logically different operations. *Fails if*: MODIFYING-style color collapse (audit §6) makes insert/update/swap indistinguishable.
3. **They can predict, just before it happens, that a swap is imminent** — because a decision beat (color shift, connecting-line, or hold) preceded the actual position exchange, rather than the swap simply starting instantly. *Fails if*: motion begins with no anticipatory cue.
4. **They notice at least one moment that feels more important than the others** — a slow-down, a camera move, a distinct sound, or a bigger visual flourish — rather than every single event feeling equally weighted. *Fails if*: all operations run at identical duration/amplitude throughout the 10 seconds.
5. **They can point to a region of the array and say "that part is done" vs. "that part is still being worked on"**, if the algorithm has run long enough to have a partially-confirmed region. *Fails if*: there's no persistent visual marker of progress and every element looks equally "in play" at all times.
6. **They do not describe the motion as "teleporting" or "snapping"** — elements that change position are seen to travel, not vanish/reappear, and elements that change value are seen to visibly react (pulse, flash) rather than silently flip. *Fails if*: any position or value change happens with a single-frame, unanimated cut.
7. **If sound is present, they don't ask "why does it keep making the same noise"** within 10 seconconds — i.e., audio varies enough with context that repetition isn't immediately grating. *Fails if*: identical unpitched sample fires on every comparison with no variation.
8. **They can distinguish "the algorithm is scanning/looking" from "the algorithm has decided/is acting"** as two different visual phases, even if they can't name which specific operation is which. *Fails if*: search/compare/evaluate phases look identical to mutate/move/commit phases (this is the vocabulary test from §1.2 restated as an outcome rather than a rule).

A redesign that passes all eight for at least one sorting algorithm and one search algorithm should be considered to have met this spec's bar for "alive and informative" — the bar is deliberately observer-behavior-based (what they notice, predict, and can articulate) rather than implementation-based, so it stays valid regardless of which specific techniques from §1 end up implemented to satisfy it.
