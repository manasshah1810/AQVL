# Array Visualization — Current State Audit

Pure diagnosis of the array visualization pipeline as it exists in the working tree today (not git history, not intended/ideal behavior). Every claim cites `file:line`. Anything not directly confirmed by reading code is marked **unverified**.

## 0. Pipeline map (what's live vs dead)

- Compiler: `packages/compiler/src/aqir/generator.ts` compiles `COMPARE`/`SWAP`/`HIGHLIGHT` statements directly to AQIR instructions `COMPARE_OBJECTS` / `SWAP_OBJECTS` / `HIGHLIGHT_OBJECT` (`packages/compiler/src/aqir/generator.ts:1078-1112`). All other array verbs (`INSERT`, `DELETE`, `UPDATE`, `PUSH`, `POP`, and the builtin sort keywords `BUBBLE_SORT`/`SELECTION_SORT`/etc.) compile to a single generic `GENERIC_ACTION` instruction carrying `actionName` + `payload.logicalParent`/`payload.logicalIndex` (`packages/compiler/src/aqir/generator.ts:1129-1163`).
- Runtime dispatch: `packages/runtime/src/core/AnimationController.ts` has exactly one class and one live entry point, `executeInstruction` (`AnimationController.ts:221`), called per-instruction from the VM (`AnimationController.ts:204`). Its `switch` handles `HIGHLIGHT_OBJECT` (`:239`), `SWAP_OBJECTS` (`:300`), `COMPARE_OBJECTS` (`:427`), and `GENERIC_ACTION` (`:517`, with an `UPDATE` branch at `:666`).
- **Dead code found**: `AnimationController.buildAnimations()` (`AnimationController.ts:2466-3620`, ~1150 lines, over 30% of the file) duplicates much of the same switch logic (its own `SWAP_OBJECTS` case at `:2482`, `COMPARE_OBJECTS` at `:2661`, `HIGHLIGHT_OBJECT` at `:2745`) but is never called anywhere in the codebase — confirmed via repo-wide grep for `buildAnimations(` returning only its own declaration. It is not part of the live render path; findings below describe only the live `executeInstruction` path plus the array-specific handlers it delegates to (`ArrayEngine`, `SortAlgorithms`).
- Array-specific op handlers that `GENERIC_ACTION` delegates to: `packages/runtime/src/core/algorithms/ArrayEngine.ts` (bare `INSERT`/`DELETE`) and `packages/runtime/src/core/algorithms/SortAlgorithms.ts` (builtin `*_SORT` keywords, registered via `AlgorithmRegistry`, `packages/runtime/src/core/algorithms/AlgorithmRegistry.ts:1-15`). `UPDATE` (and other unmatched `GENERIC_ACTION` names) is handled inline in `AnimationController.ts:666-714`, not delegated.
- Renderer: the only live array-rendering component is the generic, structure-agnostic `packages/renderer/src/components/generic/GenericSceneRenderer.tsx`, which maps every `SceneElement` with `type` in `['box','sphere','cylinder']` to a `PrimitiveNode` (`GenericSceneRenderer.tsx:15-38,99-114`) and every `type: 'edge'` element to a `PrimitiveEdge` (`:40-66,88-98`). The git-status-deleted files (`SceneElementRenderer.tsx`, `BoxRenderer.tsx`, `ArrayRenderer.tsx`, etc.) are confirmed absent from the working-tree filesystem (`find packages/renderer/src` lists only `AQVECanvas.tsx`, `camera/CameraController.tsx`, `elements/HighlightRing.tsx`, `generic/*`, `index.ts` — no per-structure renderer files exist on disk). There is no separate `ArrayRenderer`; array boxes are rendered by the same generic `PrimitiveNode` used for every other data structure's nodes.
- Tweening engine: `packages/runtime/src/core/TimelineEngine.ts` wraps `animejs` (`TimelineEngine.ts:1-3,23-47`) as a single non-autoplay timeline; `AnimationScheduler` (`packages/runtime/src/core/AnimationScheduler.ts`) queues keyframes onto it via `enqueue`/`commitGroup`/`commitSequential`. `PrimitiveNode` itself does **not** interpolate — each `useFrame` tick it snaps `groupRef.current.position.set(position.x, position.y, position.z)` directly from the prop (`packages/renderer/src/components/generic/PrimitiveNode.tsx:79-80`); the visual smoothness of moves comes entirely from anime.js mutating the underlying scene-graph element's `position`/`scale`/`color` object in small steps every animation frame, which React then re-renders — not from any spring/lerp inside the renderer for position. (Color/scale/ring *highlight* transitions do get an additional renderer-side lerp on top — see §5.)

## 1. Operation-by-operation

### INSERT (`INSERT arr[i] value`)
Handler: `packages/runtime/src/core/algorithms/ArrayEngine.ts:19-113` (only reached for a `GENERIC_ACTION` whose target is an array index; not a registered `AlgorithmRegistry` handler — dispatch is hard-coded, `ArrayEngine.ts:8-11`).

1. **Visual change**: Both position and color/scale change. All existing elements with `logicalIndex >= insertIndex` get `logicalIndex += 1` synchronously (`:29-32`), then the whole array is re-laid-out (`:55`) and every element (old + new) is tweened to its new `worldTarget` position over `duration: 500, easing: 'easeOutCubic'` (`:63-76`). The new element spawns off-scene at `position: {x:0, y:-5, z:0}` with `scale: {x:0,y:0,z:0}` and color set to the `MODIFYING` token (`:44-53`), then tweens: scale `{0,0,0}` unchanged during the 500ms shift, then a `y` bounce-in over `duration: 600, easing: 'easeOutBounce'` and a scale pop to `{1,1,1}` over `duration: 600, easing: 'easeOutBack'` (`:78-91`).
2. **Timing**: ~500ms (shift) → ~600ms (drop-in bounce, run in parallel as a separate `commitGroup`) → labels relabeled and state saved (`:94-112`). Not instant; interpolated via anime.js.
3. **Information lost**: The new element rises from `y: -5` (off-screen below the array) rather than any onscreen origin tied to where the inserted value came from — there is no visual indication of *why* index `insertIndex` was chosen or where the value originated (e.g. no source token flying in from a call site). Only the target slot and everything right of it animate; nothing distinguishes "this index is now occupied by a new object" from a plain value overwrite once the bounce settles, other than color momentarily.
4. **Visual collisions**: New element and shifted elements are colored with the `MODIFYING` token (pink, `#ec4899`/`#f472b6`, `packages/shared/src/theme/semanticColors.ts:41-47`) — the identical color used for `SWAP`, `UPDATE`, `PUSH`, `POP` (see §6).
5. **Narrative**: A `RUNTIME_LOG` event is dispatched on completion: `"Inserted value {v} at index {i} in \"{arr}\".\nElements to the right shifted one position forward.\nInsertion complete."` (`ArrayEngine.ts:104-109`). This text appears only in the separate output-console component, not overlaid on the 3D scene (see §Camera/Narrative below).

### DELETE (`DELETE arr[i]`)
Handler: `packages/runtime/src/core/algorithms/ArrayEngine.ts:121-195`.

1. **Visual change**: Target element is flagged `animationLayer = true` so the layout engine ignores it (`:137`), remaining elements with `logicalIndex > deleteIndex` get decremented and re-laid-out synchronously (`:140-141`). The target then animates `scale → {0,0,0}` over `duration: 500, easing: 'easeInBack'` while simultaneously moving `position.y += 2` over the same duration/easing (`:144-155`) — i.e., it shrinks while floating upward, then all remaining elements slide to their new `worldTarget` over `duration: 500, easing: 'easeOutCubic'` (`:158-171`), and only then is the element actually removed from the scene graph (`:178`).
2. **Timing**: ~500ms shrink-and-float-up, then ~500ms re-center shift (two sequential `commitGroup` phases, `:156,172`). Interpolated, not instant.
3. **Information lost**: Nothing marks which value was deleted after the animation completes except the preceding `RUNTIME_LOG` text; there is no persistent trace (e.g. a ghost/afterimage) once the element is removed.
4. **Visual collisions**: `AnticipationAnimation.applyAnticipation(..., 'DELETION')` (`:131`) runs first — a ~150ms pre-highlight nudge shared by the generic `AnticipationAnimation` primitive (`packages/runtime/src/core/animations/primitives/AnticipationAnimation.ts:39-127`, default `duration=150`, `easing='easeInQuad'`) that every array/tree/graph operation type also uses before its main animation, differentiated only by a small config lookup (`getAnticipationConfig`, not read in this pass — **unverified** exact per-type distinctness of the anticipation phase itself). The shrink/float used for DELETE is visually distinct from other ops (unique to this handler), so no direct collision with INSERT/UPDATE/SWAP for the main animation.
5. **Narrative**: `RUNTIME_LOG` message `"Deleted element at index {i} from \"{arr}\".\nElements to the right shifted one position back.\nDeletion complete."` (`ArrayEngine.ts:184-189`) — again console-only text, not scene-anchored.

### UPDATE (`UPDATE arr[i] value`)
Handler: inline in `packages/runtime/src/core/AnimationController.ts:666-714` (GENERIC_ACTION branch, not delegated to any Algorithm class).

1. **Visual change**: Color/emissive set to the `MODIFYING` token and scale pulses to `{1.2,1.2,1.2}` over `duration: 300, easing: 'easeOutExpo'` (`:680-694`), then back to `{1,1,1}` over `duration: 300, easing: 'easeInOutQuad'` (`:696-700`) — the element's `value` field is only mutated inside the completion callback of that shrink-back tween (`:702`), so the numeric label switches at the very end of the pulse rather than gradually. No position change at all — the element stays in its slot.
2. **Timing**: ~600ms total (300+300), scale-only, no color reset to neutral shown in this branch (color stays at the `MODIFYING` token's color after the animation — **the element does not visibly return to its idle/neutral color**, unlike COMPARE and SWAP which explicitly tween back to `neutralColor`; confirmed by absence of any follow-up color-reset enqueue in `:680-713`).
3. **Information lost**: No visual distinction between "value changed from X to Y" — the number simply flips at the end of the pulse; there is no cross-fade, no strike-through of the old value, no arrow/diff indicator.
4. **Visual collisions**: Identical `MODIFYING` color/token to INSERT, SWAP, PUSH, POP (see §6). Scale-pulse-then-settle motion is also structurally similar to COMPARE's and SWAP's scale pulses (1.15x/1.2x vs 1.2x), differing mainly in duration and the absence of the position lift/arc that COMPARE and SWAP add.
5. **Narrative**: `RUNTIME_LOG` message `"Updated value of element to {v}."` (`:705-710`) — does not name the array or index (unlike INSERT/DELETE's messages which do), so if multiple `UPDATE`s fire close together the console text alone doesn't disambiguate which array/slot changed without cross-referencing the 3D highlight timing.

### SWAP (`SWAP arr[i] arr[j]`)
Handler: `AnimationController.ts:300-425` (`SWAP_OBJECTS` case). Note: a **second, differently-tuned** SWAP implementation exists in `packages/runtime/src/core/algorithms/SortAlgorithms.ts:125-166`, used only when the builtin `BUBBLE_SORT`/`SELECTION_SORT`/etc. keyword replays its internal `SortStep` list — this is a real inconsistency: a user-written `SWAP a b` statement and the swap step inside a builtin sort look and time differently (see below).

**Direct `SWAP_OBJECTS` path** (`:300-425`, used by every example script that writes `SWAP` explicitly, e.g. `ArrayLibrary.ts:24`, `SortingLibrary.ts:12`):
1. **Visual change**: Real position exchange, not an in-place value swap. Both elements' `logicalIndex` values are swapped synchronously and the layout recomputed (`:322-328`) before either element's on-screen position moves. Elements turn `MODIFYING` pink and scale to `1.1` while lifting `y += 1.8` over `duration: 300, easing: 'easeOutExpo'` (`:330-350`); then each moves along `x`/`z` to the *other's* old lane with a `z` offset of `+1.5`/`-1.5` (an arc that displaces them to different depths so their paths don't visually overlap mid-swap) over `duration: 600, easing: 'easeInOutSine'` (`:354-372`); then they drop back down to their true `worldTarget` `y`/`z` with `duration: 350, easing: 'easeOutBounce'` (`:374-392`); then scale settles back to `1` over `duration: 300, easing: 'easeInOutQuad'` (`:394-400`).
2. **Timing**: ~300 (lift) + 200ms cursor advance (`:352`) + 600 (cross) + 350 (drop) + 300 (settle) ≈ 1750ms total, all interpolated.
3. **Information lost**: none major for this path — two elements do visibly cross positions in an arc, confirmed by the `z`-offset choreography. Labels (`arr[i]`) are only reassigned in the completion callback (`:406-407`), so during the ~1.75s animation the on-screen label under a still-moving element may briefly show its pre-swap index text until the callback fires.
4. **Visual collisions**: `MODIFYING` color, identical to INSERT/UPDATE/PUSH/POP (see §6).

**Builtin-sort SWAP path** (`SortAlgorithms.ts:125-166`, used only inside `BUBBLE_SORT`/`SELECTION_SORT`/`INSERTION_SORT`/etc. keyword scripts, e.g. `SortingLibrary.ts:141`): color pulse to `MODIFYING` + scale to `1.2` over `duration: 300` (`:131-133`), then straight `x/y/z` tween to `worldTarget` over `duration: 450, easing: 'easeInOutSine'` (`:141-147`) — **no lift, no z-offset arc, no bounce-drop**. This is a materially different, simpler motion for the "same" logical operation depending on whether the source script called `SWAP` directly or invoked a builtin sort keyword. Total time ≈ 300+450+250 ≈ 1000ms, notably shorter and flatter than the direct path's ~1750ms arc.

### COMPARE (`COMPARE arr[i] arr[j]`)
Handler: `AnimationController.ts:427-515` (`COMPARE_OBJECTS`).
1. **Visual change**: Color/emissive set to `EVALUATING` token (amber, `#f59e0b`/`#fbbf24` per `semanticColors.ts:27-33`) on both elements; scale pulses to `1.15` and elements lift `y += 0.3` over `duration: 400, easing: 'easeOutExpo'` (`:449-471`), then after a 300ms cursor advance (`:473`), scale and lift both reverse (`y -= 0.3`, scale back to 1) over `duration: 300, easing: 'easeInOutQuad'` (`:475-488`). Neither element's logical index nor world position changes — this is a pure in-place pulse/lift, no lateral movement.
2. **Timing**: 400ms up + 300ms hold (cursor advance, no visible change) + 300ms down ≈ 1000ms.
3. **Information lost**: The comparison *result* (which is greater/less) is computed and put into the `RUNTIME_LOG` text (`"{l} {symbol} {r} ({l} is {word} {r})"`, `:500-506`) but is **not** shown visually in the 3D scene at all — color/scale are identical regardless of whether the comparison is `<`, `>`, or `=`. A viewer watching only the canvas cannot tell the outcome of a compare, only that a compare happened.
4. **Visual collisions**: The `EVALUATING` amber color/pulse-lift pattern is also the canonical result of `normalizeHighlightType`/`normalizeSemanticState` for the aliases `COMPARE, COMPARING, CHECKING, ACTIVE, SELECTING, SELECT, KEY` (`packages/shared/src/theme/highlightStyle.ts:64-74`, `packages/shared/src/theme/semanticColors.ts:86-98`) — so a plain `HIGHLIGHT` on a "selected"/"active"/"key" element (no explicit `'SUCCESS'`/other color literal) can visually read identically to a COMPARE, though `HIGHLIGHT_OBJECT`'s own code path (`AnimationController.ts:239-297`) actually defaults its color token to `'SUCCESS'` (green) unless the script passes an explicit color string, so in practice `HIGHLIGHT arr[i]` (no second argument) is green, not amber — the collision is at the *token-normalization* layer (would apply if a script or algorithm explicitly requested `HIGHLIGHT ... 'ACTIVE'`/`'SELECT'`/etc.), not the common default case. **Confirmed collision that is common in practice**: COMPARE (amber, pulse+lift) has a *different* animation shape from generic default HIGHLIGHT (green, pulse only, no lift) — so these two are visually distinguishable by color, but COMPARE has no distinguishable "found true" vs "found false" visual variant.
5. **Narrative**: `RUNTIME_LOG` compare text described above (`:504-509`) is the only place a comparison's outcome/direction is expressed. Purely console text.

### HIGHLIGHT (`HIGHLIGHT arr[i]` / `HIGHLIGHT arr[i] 'SUCCESS'`)
Handler: `AnimationController.ts:239-297`.
1. **Visual change**: Color/emissive set from `getSemanticColorToken(hl.color || 'SUCCESS')` (`:245`) — i.e. green by default, or whatever token the script names. Scale pulses to `1.15` over `duration: 400, easing: 'easeOutExpo'` (`:261-266`), advances cursor 200ms, then scale returns to `1` over `duration: 300, easing: 'easeInOutQuad'` (`:271-277`). No position change.
2. **Timing**: ~900ms (400+200+300).
3. **Information lost**: `isHighlighted = true` and `state`/`highlightType` are left set permanently on the element after the animation completes (`:246-248`) — there is no "un-highlight" instruction path visible in this switch, so once highlighted (e.g. in a traversal loop that highlights many elements in sequence, as in `ArrayFoundation`'s `LOOP i FROM 0 TO 4 → HIGHLIGHT arr[i]`), an element apparently stays visually "active" (scaled/colored per `isElementActive`, `highlightStyle.ts:150-170`) indefinitely rather than being reset to neutral — **this could not be fully confirmed without runtime inspection**; it depends on whether a later instruction (e.g. the next loop iteration's `HIGHLIGHT`) or some other reset path clears the previous element's `isHighlighted`/`state`. No explicit reset code was found in this handler. Marked **unverified — needs runtime inspection**.
4. **Visual collisions**: Same scale-pulse envelope shape (`1.15x`, `easeOutExpo` in/`easeInOutQuad` out) as COMPARE, differing only in color and the absence of COMPARE's `y`-lift.
5. **Narrative**: `RUNTIME_LOG` message names the array/index/value (`"Highlighted {arr}[{i}] — value: {v}"`, `:285-292`).

### Index access / read (e.g. `x = arr[i]`, no explicit `HIGHLIGHT`)
1. **Visual change**: none. `ExpressionStatementNode` compiles a bare assignment via `tryGenerateAssignment`/`compileValue` (`packages/compiler/src/aqir/generator.ts:1189-1198`) which resolves purely to VM value operations — no AQIR instruction is emitted for the read itself. Confirmed by grepping the generator's statement-type switch (`generator.ts:1076-1201`): `ArrayAccessNode` reads only appear as arguments inside `CompareNode`/`SwapNode`/`GenericActionNode`/expression compilation, never as their own emitted instruction.
2. Example confirming this: `MaximumSubarrayKadane` (`packages/demo/src/examples/ArrayLibrary.ts:80-107`) reads `arr[i]` inside arithmetic (`currentSum = currentSum + arr[i]`) with zero visual effect from the read itself — only the explicit `HIGHLIGHT arr[i]` calls around it produce any scene change.

### Resize / growth beyond declared length
No dedicated "resize" instruction or handler was found anywhere in `packages/compiler/src/aqir` or `packages/runtime/src/core/algorithms`. `INSERT` grows the array by one slot at a time via `ArrayEngine.insert` (§ above); there is no bulk-resize, capacity-doubling, or "array full" visualization. **Unverified** whether any DECLARE-time array-size limit exists in the semantic validator (not read in this pass) — the layout-and-animation code shows no capacity ceiling logic.

## 2. Camera behavior

`packages/renderer/src/components/camera/CameraController.tsx` drives the camera every `useFrame` tick (`:108-170`). Default mode is `AUTO_FIT` (no explicit `CAMERA` statement in a script) (`:111`): it computes the mean X and the X-span of all current scene elements (`:33-62`) and lerps the orbit target toward that mean with `LERP_TARGET = 0.04` (`CameraController.tsx:27,121-122`), and if the array's X-span exceeds `6` units it also lerps the camera's `z` distance toward `Math.max(10, Math.min(30, 8 + spanX * 0.75))` with `LERP_ZOOM = 0.03` (`:28,123-126`) — i.e. the camera does zoom out as the array's on-screen width grows, but only continuously re-centers/re-zooms while `autoFollowRef.current` is true, which becomes `false` the moment the user manually drags the `OrbitControls` (`:80-85,102-104`), after which the camera holds still until a "Reset Camera" click (`AQVECanvas.tsx:17-19,24-47`) re-enables auto-follow. Other modes (`FOCUS`, `ORBIT`, `POSITION`, `:130-160`) exist and are lerped but only activate if a compiled `SET_CAMERA`/`CAMERA` AQIR frame is present on `sceneState.camera`; none of the traced array examples (Bubble/Insertion/Selection sort scripts, `ArrayFoundation`, `LinearSearch`, `BinarySearch`) contain a `CAMERA` statement, so **all traced examples run purely in `AUTO_FIT`** — confirmed by absence of any `CAMERA`/`FOCUS` keyword in `SortingLibrary.ts`, `SearchingLibrary.ts`, `ArrayLibrary.ts`.

## 3. Element visual design (shape / color / legibility / index labels)

- Shape: array elements always render as `RoundedBox` (`type: 'box'`) — `PrimitiveNode.tsx:124-143` — a rounded cube, `args=[1,1,1]` with bevel radius from `MATERIAL_PRESETS.NODE.bevelRadius = 0.1` (`materialSystem.ts:33-41`). Spheres/cylinders exist in the same component but are not used for `ARRAY_ELEMENT` (their `logicalParent`/`originalType: 'ARRAY_ELEMENT'` tagging is always type `'box'`, confirmed in `ArrayEngine.ts:37` and `ArrayLayoutStrategy.ts:30` which filters `el.type === 'box'`).
- Note: `HighlightRing.tsx:63-64` explicitly suppresses the ring torus for `type === 'box'` (`"Remove skeleton box around box elements during operations"`) — meaning the pulsing halo ring effect used for spheres/cylinders (drawn in `PrimitiveNode.tsx:175-180`) **never renders for array elements at all**; array elements' only highlight cue is the material color/emissive/scale change, not the ring.
- Color/idle state: neutral idle color for a non-active array element is whatever `context.defaultColor` was set to at scene-build time (referenced in `SortAlgorithms.ts:101,122,151` as `neutralColor`); not traced further in this pass (**unverified** exact hex — depends on `AlgorithmContext.defaultColor` construction, not read).
- Value label: rendered as a 3D `<Text>` at `fontSize={0.4}`, white (`#ffffff`), centered in front of the box (`PrimitiveNode.tsx:182-192`, `labelZOffset = 0.51` for boxes, `:119`). Index/array-name label (e.g. `arr[2]`) rendered as a second `<Text>` below the box at `fontSize={0.25}`, gray (`#aaaaaa`) (`:194-204`). Both are billboard-style `Text` from `@react-three/drei` — **unverified** whether they auto-face the camera (drei's `Text` does by default but this wasn't confirmed by reading drei's source in this pass).
- Legibility at scale: font sizes are fixed absolute world-units (`0.4`/`0.25`) regardless of array length; they do not shrink or grow with element density (see §5).

## 5. Small-vs-large-array behavior (scale)

- Spacing: `ArrayLayoutStrategy` (`packages/runtime/src/core/layouts/ArrayLayoutStrategy.ts`) uses a **fixed** `spacing = 2.2` world units between adjacent elements regardless of array length (`:22,40-54`, default from constructor options, not itself a function of element count). `totalLength = (n-1) * spacing` grows linearly with `n` (`:40`), and elements are centered around `startX` (`:47`). There is no branch anywhere in this file that reduces `spacing` as `n` grows — confirmed by reading the entire 59-line file; the only conditional logic is `direction === 'horizontal'` vs vertical layout (`:46-52`).
- Consequence for small arrays (e.g. 5-7 elements, matching every traced example: `BubbleSort` has 7, `SelectionSort` has 5, `LinearSearch` has 7): total on-screen width ≈ `(n-1)*2.2` world units, e.g. 6 gaps × 2.2 = 13.2 units for a 7-element array — comfortably inside the `AUTO_FIT` camera's "zoom starts increasing past span 6" threshold (`CameraController.tsx:123`), so these examples do trigger camera zoom-out, confirmed by `spanX` (≈13.2) exceeding `6`.
- Consequence for large arrays (e.g. 100 elements, **not directly tested — no example in the library has anywhere near 100 elements**; largest found is `TernarySearch`/`InterpolationSearch` at 10, `ArrayFoundation` at 5): projecting the same fixed-spacing formula, a 100-element array would span `99 * 2.2 = 217.8` world units. The `AUTO_FIT` zoom clamps `idealZ` to `Math.min(30, 8 + spanX*0.75)` (`CameraController.tsx:124`) — i.e. camera distance caps at 30 units regardless of how wide the array gets, meaning a very large array would be zoomed out only up to a fixed maximum distance and elements/labels would become proportionally tiny or extend off-screen; there is no found mechanism (grid-wrapping, compression, level-of-detail, or camera-side scaling of element size) that adapts the array's world-space footprint or the fixed `fontSize={0.4}`/`0.25` text scale to element count. This is a **static/traced, not executed**, projection from the fixed-spacing formula and fixed camera-distance cap — not confirmed by actually running a 100-element example (none exists in the demo library, and no CLI harness to author a custom test script was located within scope of this pass — see §6 below).
- No adaptive/dynamic-spacing or "compress for large N" code path was found in `ArrayLayoutStrategy.ts`, `LayoutManager.ts`, or `computeDefaultLayoutParams` (`packages/compiler/src/codegen/defaultLayoutParams.ts` — file located but not read in full in this pass; **unverified** whether it varies spacing by declared array size at compile time rather than at runtime layout time). This gap should be treated as **unverified** rather than "confirmed absent" for the compile-time default-params path specifically, since that file's contents were not inspected line-by-line.

## 6. Cross-operation visual collisions (color/token layer)

Two parallel palettes exist and are both consulted at render time:
- `HIGHLIGHT_PALETTE` in `packages/shared/src/theme/highlightStyle.ts:30-55` (consumed by `PrimitiveNode`'s ring/accent-color logic, `PrimitiveNode.tsx:62,118`).
- `SEMANTIC_PALETTE` in `packages/shared/src/theme/semanticColors.ts:19-76` (consumed directly by `AnimationController`/`ArrayEngine`/`SortAlgorithms` to set `el.color`/`el.emissiveColor` before the anime.js tween runs, e.g. `getSemanticColorToken('MODIFYING')` at `ArrayEngine.ts:34`, `SortAlgorithms.ts:99-100`, `AnimationController.ts:308,674`).

Both palettes' `normalizeHighlightType`/`normalizeSemanticState` functions group the following operation names into a **single indistinguishable color+animation-envelope bucket**:
- **MODIFYING** (pink `#ec4899`/`#f472b6` per `semanticColors.ts:41-47`, or `#f472b6`/`#ec4899` per `highlightStyle.ts:35-38` — the two palettes even swap which hex is "color" vs "emissive" between themselves, though the two values used are the same pair): covers `MODIFY, SWAP, SWAPPING, INSERT, INSERTING, UPDATE, REPLACE, PUSH, POP` (`highlightStyle.ts:76-86`) and additionally `INSERT_HEAD, INSERT_TAIL, UPDATING, REPLACING, REORDER` in the semantic-colors variant (`semanticColors.ts:115-130`). **Confirmed from the actual handler code (not just the palette table)**: INSERT (`ArrayEngine.ts:34,46`), UPDATE (`AnimationController.ts:674`), and SWAP (both `AnimationController.ts:308` and `SortAlgorithms.ts:99,131`) all literally call `getSemanticColorToken('MODIFYING')` and set the identical color/emissive pair — this is not merely a theoretical palette overlap, it is the actual code path for three of the four core array-mutation operations.

## 7. Narrative / "why" gap assessment

- There is no in-scene caption, tooltip, or overlay tied spatially to a highlighted/moving element. `AQVECanvas.tsx` (`packages/renderer/src/components/AQVECanvas.tsx:1-103`) contains only a "Reset Camera" button as UI chrome (`:24-48`) inside the canvas container; no text/label overlay component is mounted alongside `GenericSceneRenderer`.

This is a structural gap between the visual layer and the explanatory layer, not merely a missing label — the two are rendered by entirely separate components that only share data through the `RUNTIME_LOG` event bus.
