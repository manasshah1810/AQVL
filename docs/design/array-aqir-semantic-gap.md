# Array Animation — AQIR Semantic Gap Analysis

Purpose: for each capability in `array-animation-excellence-spec.md`, determine whether the AQIR instruction/type system as it exists in the working tree today already carries the data needed, and if not, specify the precise data-shape fix (new field / new instruction / new non-instruction metadata layer). This is a data-shape analysis only — no implementation plan, no timeline. Every claim cites `file:line`; anything not directly confirmed is marked **unverified**.

## 0. The instruction model, as it actually exists today

Two parallel instruction families exist, both flowing through one `VMInstruction` union (`packages/compiler/src/aqir/types.ts:69`):

- **Legacy action-based instructions** (`AQIRInstruction extends { action: string }`, `packages/shared/src/aqir/types.ts:23-25`): `CompareObjectsInstruction {action,leftId,rightId}` (`:28-32`), `SwapObjectsInstruction {action,leftId,rightId}` (`:35-39`), `HighlightObjectInstruction {action,targetId,color}` (`:42-46`), `GenericActionInstruction {action,actionName,targetId?,args}` (`:72-77`), plus `WaitInstruction`, `LinkObjectsInstruction{sourceId,targetId,directed,relationType?}`, `LoopInstruction`, `SetStateInstruction`, `UpdateLayoutInstruction`.
- **New VM-mode control-flow opcodes** (`packages/compiler/src/aqir/InstructionSet.ts:29-49,176-183`): `JUMP`, `JUMP_IF_FALSE`, `CALL`, `RET`, `PUSH_SCOPE`, `POP_SCOPE`, `SET_VAR` — pure control flow, carry no array-semantic data.
- **Geometry opcodes** (same file, `:196-300`): `SET_LAYOUT_STRATEGY`, `SET_POSITION`, `COMPUTE_LAYOUT`, `SET_CAMERA{mode,params:{targetId?,speed?,x?,y?,z?}}`, `SET_ROTATION`, `SET_SCALE`.

**Undeclared field found**: the generator emits `GENERIC_ACTION` instructions with a `payload: { logicalParent, logicalIndex }` field (`packages/compiler/src/aqir/generator.ts:1156-1162`) that does **not exist** on the `GenericActionInstruction` interface (`packages/shared/src/aqir/types.ts:72-77` has only `action, actionName, targetId?, args`) — the emit call is cast `as any` (`generator.ts:1162`) to bypass the type check. Every runtime consumer (`ArrayEngine.ts:20-21`, `SortAlgorithms.ts:56`, `AnimationController.ts:526,551`) reads it back via `(gen as any).payload?.logicalParent`. This is a real, exploitable gap for Phase 2: `payload` is already the de facto extension point for "extra context the compiler knows but the formal type doesn't declare," and any new per-instruction field this document proposes for `GENERIC_ACTION` can piggyback on formalizing this same object rather than inventing a new channel.

**Compiler algorithm-level visibility**: confirmed via the parser that builtin sort keywords (`BUBBLE_SORT`, `SELECTION_SORT`, etc.) are parsed as a plain generic action (`packages/compiler/src/parser/index.ts:680-681`, routed through `parseGenericAction()`), and the generator's `GenericActionNode` case (`generator.ts:1129-1163`) treats it exactly like `INSERT`/`UPDATE`/`PUSH` — one `GENERIC_ACTION` instruction with `actionName:'BUBBLE_SORT'` and `payload.logicalParent` (the array name), nothing else. **The compiler has zero visibility into algorithm-level structure** (passes, pivot, phase, comparisons-that-swap) for builtin sorts — this isn't a case of "known but unthreaded," it's genuinely not computed at compile time at all. That computation happens entirely at runtime, one level below AQIR:

**The `SortStep` layer is not AQIR.** `packages/runtime/src/core/algorithms/SortEngine.ts` runs the *entire* sort synchronously in plain JS before any animation is scheduled (`SortAlgorithms.ts:79-96` calls e.g. `SortAlgorithm.bubbleSort(values, comparator)` and gets back a complete `result.steps: SortStep[]` array up front), then `SortAlgorithms.runSort` (`SortAlgorithms.ts:108-209`) replays that pre-computed list into scheduler calls one at a time. This means: (a) full lookahead over the entire algorithm trace already exists in memory at replay time, for free, before a single animation frame is scheduled — nothing about pacing or "is this the decisive comparison" is unknowable, it's simply not attached to each `SortStep`; (b) this whole subsystem — `SortStep`, `SortResult`, `SortEngine.ts` — is internal to the runtime's `SortAlgorithms` handler and **never becomes an AQIR instruction**; the compiler and the AQIR instruction stream see only the single opaque `GENERIC_ACTION{actionName:'BUBBLE_SORT'}`. Consequently, gaps in per-algorithm signature data (§2 below) are correctly categorized as **enrichment to a runtime-internal step model**, not as AQIR instruction changes — a materially different (and cheaper) fix than adding compiler/AQIR fields, since it requires no compiler changes at all, only edits to `SortEngine.ts`'s step-producing loops and `SortAlgorithms.ts`'s consumption of them.

`SortStep` today (`SortEngine.ts:19-25`) is exactly:
```ts
type SortStep<T = number> =
  | { type: 'COMPARE'; i: number; j: number }
  | { type: 'SWAP'; i: number; j: number }
  | { type: 'OVERWRITE'; i: number; value: T }
  | { type: 'PIVOT'; i: number };
```
No `outcome`, `pass`/`depth`, `isFinal`/`confirms`, or `decisive` field exists on any variant.

## 1. Techniques

### 1.1 Weight and anticipation

**(a) Supported today.** This is a pure rendering/timing concern and needs **no AQIR or instruction-schema change at all** — confirmed by reading the actual mechanism. `AnticipationAnimation.applyAnticipation` (`packages/runtime/src/core/animations/primitives/AnticipationAnimation.ts:43-126`) already runs a distinct pre-motion (duration/easing/scale/nudge/preview-color) sourced from `getAnticipationConfig(typeOrAlias)` (`:59`), which is a **per-operation-type table**, `ANTICIPATION_PALETTE: Record<AnticipationType, AnticipationConfig>` (`packages/shared/src/theme/anticipationSystem.ts:35`), with confirmed distinct entries for `COMPARISON`, `SWAP`, `INSERTION`, `DELETION`, etc. (verified via the type's own test file, `packages/shared/src/theme/anticipationSystem.test.ts:18-53`, which asserts distinct `previewSemanticState` per type: swap→`MODIFYING`, compare→`EVALUATING`, deletion→`DISCARDED`). This resolves the current-state audit's "unverified" note about per-type anticipation distinctness (audit §"DELETE.4") — **confirmed distinct, not unverified**. Both the direct-`SWAP` unification and asymmetric COMPARE lift/fall timing the spec asks for are pure duration/easing-curve choices inside this existing per-type config — no new data needs to reach the instruction.
**(b) Gap**: none at the instruction-data level. The only real issue (already documented in the audit) is that the builtin-sort SWAP path (`SortAlgorithms.ts:130`, `applyAnticipation(..., 'SWAP')`) and the direct-`SWAP_OBJECTS` path (`AnimationController.ts:300+`, which does **not** call `AnticipationAnimation.applyAnticipation` at all — confirmed absent from that code path by inspection of `:300-425`) diverge in whether they use the shared anticipation primitive in the first place. That's a handler-code inconsistency, not a data-shape gap — no fix belongs in this document.

### 1.2 Color/emphasis vocabulary

**(a) Supported today, partially.** The palette already has **8 states**, more than the spec's minimum 5: `NEUTRAL, EVALUATING, TRAVERSING, MODIFYING, SUCCESS, DISCARDED, AUXILIARY, STRUCTURAL` (`packages/shared/src/theme/semanticColors.ts:1-9,19-76`). Distinct hex values already exist for something close to every spec role: amber `EVALUATING` (`:27-33`, matches spec's amber), green `SUCCESS` (`:48-54`, matches spec's confirmed/green), muted gray `DISCARDED` (`:55-61`, closest existing analog to spec's "red/orange, decided/about to move" role, though the color itself is gray not red/orange), violet `AUXILIARY` (`:62-68`, matches spec's "blue/violet, in transit" role by hue). **This means the 5-state vocabulary is achievable today with zero new palette tokens or type changes** — it is a token-*selection* problem in the handler code, not a data-model gap: `COMPARE_OBJECTS` and `SWAP_OBJECTS` handlers simply never call `getSemanticColorToken('DISCARDED')` or `getSemanticColorToken('AUXILIARY')`, hardcoding `EVALUATING`/`MODIFYING` instead (`AnimationController.ts:435,308`). No fix in this document is needed for "does a suitable color exist" — it does.

**(b) Gap — COMPARE outcome divergence.** This is a genuine data gap, precisely located: the comparison outcome (`<`/`>`/`=`) is computed **only** inside the completion callback of the animation, at `AnimationController.ts:500-501` (`const cmpSymbol = lVal < rVal ? '<' : ... ; const cmpWord = ...`), immediately before it's written into the `RUNTIME_LOG` text at `:504-509`. It is computed from `leftEl.value`/`rightEl.value`, which are already resolvable the instant `COMPARE_OBJECTS` begins executing (`leftEl`/`rightEl` are fetched at `:429-430`, before any animation is enqueued) — **the outcome is not "unknown until later," it is trivially known up front and simply not computed until the callback**. This is the one clear case in the whole audit of "compiler/runtime already has the data, it's just not threaded to where the color decision is made."
  - **Precise fix — no new instruction, no new field on `CompareObjectsInstruction` needed.** `CompareObjectsInstruction` itself (`leftId`, `rightId`) does not need an `outcome` field, because the outcome depends on the two elements' *current runtime values*, which can change between compile time and execution time (loop-driven comparisons compare different values each iteration) — baking an outcome into the AQIR instruction at compile time is not meaningful (the compiler cannot know runtime array contents). Instead: **the fix belongs entirely inside the `COMPARE_OBJECTS` handler in `AnimationController.ts`**, moved earlier. Concretely: compute `const cmpSymbol = ...` immediately after `leftEl`/`rightEl` are resolved (right after `AnimationController.ts:430`, before the `EVALUATING` color/animation is enqueued at `:442-471`), and use that outcome to select which existing semantic token (`EVALUATING` while pending, then `DISCARDED`/`AUXILIARY`/`SUCCESS` — whichever the redesign phase assigns to "loses"/"wins"/"in transit" — once resolved) each element gets in the second animation phase (`:475-488`, currently just a scale/position reversal with no color change). This is a **handler-logic reordering**, not an AQIR schema change, since `leftEl.value`/`rightEl.value` are already `SceneElement` fields fully populated before `COMPARE_OBJECTS` starts.
  - The same reasoning applies to `SortAlgorithms.ts`'s inline `COMPARE` step handling (`:108-124`) — it never computes an outcome at all today (only logs "Compare X and Y" at `:120`), but `elA.value`/`elB.value` are available at the same point, so the fix there is identical in kind: compute the comparator result before enqueueing the color animation, not after.

**(b) Gap — SWAP's "about to move" vs "in transit" color split.** `SwapObjectsInstruction` (`leftId, rightId`) carries no phase concept, and none is needed as new instruction data: the two-phase color transition (red/orange pre-decision → blue/violet in-transit) is entirely something the **handler** can express by calling `getSemanticColorToken` twice with two different existing tokens at two different points in the already-multi-phase tween sequence it runs (`AnimationController.ts:330-400` already has 4 sequential phases — lift, cross, drop, settle — it simply reuses one color, `MODIFYING`, across all of them). **No AQIR/type change required**; this is a handler-code sequencing change using tokens that already exist.

**(b) Gap — "confirmed sorted" persistent green state.** No mechanism exists anywhere to mark an array element as permanently `SUCCESS`/sorted-final. See §3C below (same underlying gap, addressed once there in full).

### 1.3 Camera as attention director

**(a) Supported today, narrowly.** `SET_CAMERA`'s `FOCUS` mode (`SetCameraInstruction`, `packages/compiler/src/aqir/InstructionSet.ts:250-263`) takes exactly one `params.targetId?: string` (confirmed singular by both the type — `:254` — and the generator, which resolves a single `this.resolveExpressionId(node.target)` at `generator.ts:995`, and the runtime's `FOCUS` handling in `CameraController.tsx:130-138`, which reads one `cameraState?.targetId` and looks up one element). `AUTO_FIT` (the mode every traced array example actually runs in) reacts only to the mean X and X-span of *all* elements (`CameraController.tsx:33-62,117-128`) — it has no concept of "which elements are currently the subject of the active instruction."
  - **Confirmed: `SET_CAMERA` is never emitted automatically.** Repo-wide check of every place `SET_CAMERA`/`sceneState.camera` is touched (`packages/runtime/src/VirtualMachine.ts:370+`, the only place that resolves the opcode into `cameraState`) shows it is populated exclusively from an explicit `CAMERA` statement compiled by `generateCameraStatement` (`generator.ts:991-1009`). Neither `COMPARE_OBJECTS`/`SWAP_OBJECTS`'s handlers in `AnimationController.ts` nor `SortAlgorithms.ts`'s step replay ever dispatch or synthesize a camera instruction — confirmed by grep, no `SET_CAMERA`/`camera` reference appears in either file.
**(b) Gap, precisely.** Two independent problems, two independent fixes:
  1. **`FOCUS` cannot target a pair.** `SetCameraInstruction.params` needs a new field: add `targetIds?: string[]` alongside the existing singular `targetId?: string` (kept for backward compatibility with existing single-target `CAMERA FOCUS(x)` scripts) to `SetCameraInstruction['params']` (`InstructionSet.ts:253-262`), and `CameraFrameState` in `packages/runtime/src/aqir/types.ts` needs the mirrored field, and `CameraController.tsx`'s `FOCUS` case (`:130-138`) needs to compute a centroid/bounding-lerp-target over `targetIds` when present instead of the current single-element lookup. **This is a field addition to an existing instruction type**, not a new instruction.
  2. **Nothing tells the camera when a compare/swap is happening or who the participants are**, because no instruction is ever synthesized for it. This is **not** a gap in `COMPARE_OBJECTS`/`SWAP_OBJECTS` themselves (both already carry `leftId`/`rightId` — full participant identity is already present on the instruction that would need to trigger the camera reaction). The gap is architectural: **the fix is a new metadata/behavior layer, not a new field on `CompareObjectsInstruction`/`SwapObjectsInstruction`.** Two shapes are consistent with the existing model and are both viable (a redesign-phase decision, not this document's call): either (i) the `AnimationController`'s `COMPARE_OBJECTS`/`SWAP_OBJECTS` handlers synthesize a runtime-only camera-focus call (using the fix in (1) above) as a side effect when they already have `leftEl`/`rightEl` resolved — no new AQIR instruction needed since the instruction already carries the ids, only new *handler behavior* — or (ii) a genuinely new, purely-visual instruction, e.g. `FOCUS_HINT{ targetIds: string[], priority: number, ttlMs: number }`, emitted by the same handlers, kept decoupled from `SET_CAMERA`'s scripted-camera semantics so a user's own `CAMERA` statement isn't silently overridden. Recommend (ii) if the redesign wants "camera reaction is opt-outable/tunable independent of instruction semantics" — that's a new-instruction-type fix; (i) is a zero-new-type, handler-only fix. Both are precise and buildable; this document does not pick one.

### 1.4 Sound

**(a) Supported today: none.** Confirmed absent (audit §4, re-verified here) — zero audio infrastructure anywhere in the repo.
**(b) Gap, but the underlying data is already present — this is almost entirely a renderer/runtime-side addition, not an AQIR gap.** Pitch-by-magnitude needs the compared values, already on `leftEl.value`/`rightEl.value` (`SceneElement.value`, populated before `COMPARE_OBJECTS` starts, `AnimationController.ts:429-430`). Pan-by-position needs each element's world position, already on `leftEl.position`/`rightEl.position` (same objects). **No new instruction field is needed for pitch or pan.** The one piece of sound-relevant data that genuinely doesn't exist yet is the same COMPARE-outcome gap already described in §1.2 — if a distinct "swap incoming" tone (vs. a neutral tick) is wanted the instant a comparison resolves, it depends on the same outcome computation being moved earlier, not on new instruction fields. **Categorization: new metadata layer only in the sense that "which sound to play" is itself a new (non-AQIR) mapping table analogous to `ANTICIPATION_PALETTE`/`SEMANTIC_PALETTE` — a `SOUND_PALETTE`-shaped lookup by operation type — not a change to any instruction shape.**

### 1.5 Variable pacing

**(a) Supported today: no pacing hint of any kind exists on any instruction** — confirmed: `CompareObjectsInstruction`, `SwapObjectsInstruction`, and `SortStep` all carry zero duration/priority/significance field; every duration is a hardcoded literal in the handler (`AnimationController.ts:454,461,469`, etc.; `SortAlgorithms.ts:115-152` uses fixed 250/300/450ms literals throughout).
**(b) Gap, but split cleanly by which code path it affects — this is the document's clearest illustration of "knowable but unthreaded" vs. "needs new data added":**
  - **Builtin-sort path (`SortAlgorithms.ts`): no new field is architecturally required**, because — as established in §0 — `result.steps` is the *entire, already-computed* trace before replay starts (`SortAlgorithms.ts:79-96`). Whether a given `COMPARE` step is "decisive" (immediately followed by a `SWAP` on the same pair) or "routine" (not) is answerable today by peeking `result.steps[idx+1]` inside the `forEach` in `runSort` (`:108`) with **zero schema change** — the information already exists in the array the loop is iterating, just not surfaced per-step. Likewise "early pass vs. late pass" is recoverable from the loop's own position in `result.steps` (or, more directly, from re-threading the outer-loop index `i`/`pass` that `SortEngine.ts`'s `bubbleSort`/`selectionSort`/`insertionSort` loops already have in scope at push-time, e.g. `bubbleSort`'s outer `for (let i ...)` at `SortEngine.ts:55` — trivial to attach as a field). **Recommended precise fix (optional convenience, not a hard requirement): add `pass?: number` and `decisive?: boolean` fields to the `SortStep` union** (`SortEngine.ts:19-25`), populated at push time in each algorithm's loop (e.g. `bubbleSort` already knows `i` — the pass — and already knows, one line later, whether the comparison triggered a swap — trivial to backfill `decisive` onto the just-pushed `COMPARE` step once the `if (comparator(...) > 0)` branch resolves, `SortEngine.ts:58-64`). **This is a new-metadata-layer fix (enriching the runtime-internal `SortStep` model), not an AQIR instruction change**, since `SortStep` never becomes AQIR.
  - **Direct-script `COMPARE`/`SWAP` path (`AnimationController.ts`): a genuine gap with no free lunch.** A user-authored script's `COMPARE arr[i] arr[j]` followed by an `IF ... SWAP arr[i] arr[j]` are two independent AQIR instructions with no linkage field between them — unlike the builtin-sort path, there is no pre-computed lookahead array to peek into; the VM executes one instruction at a time (`pc`-driven, `packages/compiler/src/aqir/types.ts:114-118`). Determining "is this comparison about to trigger a swap" for the direct-script path would require either (i) a **runtime one-instruction lookahead** in `AnimationController`/the VM (peek `instructions[pc+1..pc+3]` for a same-pair `SWAP_OBJECTS` before committing to the `COMPARE_OBJECTS` animation's pacing) — a VM/controller-level change, not an instruction-schema change, since it just reads instructions already in the array — or (ii) accept that pacing significance for hand-written scripts is unknowable without executing further and use a coarser proxy (e.g. always render direct-script COMPAREs at a fixed "no lookahead available" pace, reserving the fast/slow distinction for builtin-sort-driven comparisons only). This document does not resolve which; it flags option (i) as buildable with no new field (VM already has the flat, indexed instruction array) and option (ii) as a scope-reduction decision for the redesign phase.

## 2. Algorithm distinguishability

All five named signatures depend on data that lives exclusively in the runtime-internal `SortStep`/`SortEngine.ts` layer (§0) — **none of this reaches AQIR today, and none of it needs to**, since the compiler has no visibility into algorithm internals for builtin sorts (confirmed §0) and per-algorithm signature data is naturally a runtime-replay-time concern, not a compile-time one.

- **Bubble Sort — shrinking active region / "green frontier."** `SortEngine.ts:55-68`'s outer loop already reduces the inner loop's upper bound (`n - i - 1`) each pass — the shrinking boundary is implicit in loop bounds but **never surfaced as data**: no step or field says "index `n-1-i` is now confirmed final" after each outer-loop pass. **Gap: new field on `SortStep`, not a new instruction.** Recommend a new `SortStep` variant, e.g. `{ type: 'FINALIZE'; i: number }`, pushed once per outer-loop iteration right after the inner loop completes (`SortEngine.ts:66`, i.e. after the `if (!swappedInPass) break;` check, push `FINALIZE` for index `n-1-i`). This is fully knowable at push time — the loop already knows which index just became untouchable.
- **Selection Sort — fixed candidate + full sweep + one decisive swap.** `SortEngine.ts:80-94` already has exactly this shape in the *algorithm's* control flow (one `minIdx` tracked across the full inner sweep, one `SWAP` per outer iteration if `minIdx !== i`) — but the emitted `COMPARE` steps (`:83`) don't distinguish "the running candidate" from "just being probed," and there's no step marking the boundary index `i` as the fixed candidate for the UI to hold a distinct visual on. **Gap: new field/step, runtime-internal.** Two options, both precise: (i) add a `candidate?: number` field to the `COMPARE` step variant so each comparison step names which index is the current best-so-far, populated from `minIdx` at push time (`:83`, trivial — `minIdx` is already in scope); or (ii) reuse the pattern already established for quick sort's pivot (a dedicated `{ type: 'CANDIDATE'; i: number }` step) pushed once at the start of each outer pass and again whenever `minIdx` changes (`:86-87`). Either is a `SortStep` enrichment, not an AQIR change. Same `FINALIZE` step as bubble sort applies after each swap places the found minimum (`:91`, boundary advances).
- **Insertion Sort — variable-length backward walk within growing sorted prefix.** `SortEngine.ts:106-120`'s `while (j > 0)` loop already produces the variable-length-burst structure for free (each outer `i` walks back a different number of steps) — **no new field is needed for the "variable length" part; it's already implicit in how many consecutive `COMPARE`/`SWAP` steps appear per outer iteration**, which any replay-side burst-length pacing (§1.5) can measure directly. The only missing piece is the same `FINALIZE`/growing-sorted-prefix marker as above: no step currently signals "prefix `[0..i]` is now sorted" after each outer iteration completes (`:107`, after the `while` loop exits). **Gap: same `FINALIZE`-step fix as bubble/selection, reused.**
- **Merge Sort — simultaneous spatially-separated regions + converging merge-frontier.** This is the hardest case and only **partially** knowable eagerly. `mergeSortRecurse` (`SortEngine.ts:146-159`) and `merge` (`:167-211`) already know, at push time, the exact `left`/`mid`/`right` bounds of every merge call — so "which two regions are being merged" is fully knowable and simply not attached to the `OVERWRITE`/`COMPARE` steps pushed inside `merge` (`:183,187,191,199,206`). **Gap: add `left`, `mid`, `right` (the current merge call's bounds) to the `COMPARE` and `OVERWRITE` step variants** (or a wrapping `mergeId`/`depth` counter unique per `mergeSortRecurse`/`merge` invocation), populated trivially since `merge`'s parameters already carry exactly this. This is what lets a renderer group simultaneously-active regions and draw a converging frontier. **However**, whether a given `merge` call's resulting range `[left,right]` is *globally* final (spec §3C's "confirmed sorted," not just "these two runs are now interleaved with each other") is **only true for the outermost call** (`left===0 && right===array.length-1`) — an inner merge's output range gets rewritten by a later, larger enclosing merge. This is a genuine "not simply knowable as a per-step boolean without tracking recursion identity" nuance, marked **unverified whether a simpler proxy (e.g. depth===0) is sufficient** versus needing explicit call-tree bookkeeping — flagged for the redesign phase rather than resolved here. **Categorization: new fields on existing `SortStep` variants (`left/mid/right` or a call-scoped id), runtime-internal — not an AQIR change**, plus an open question (not a settled gap) about final-region semantics for nested merges.
- **Quick Sort — held pivot + converging cursors + split-after-lock-in.** `partition` (`SortEngine.ts:254-286`) already emits a `PIVOT` step at selection time (`:263`) — this part is **already supported** (`type: 'PIVOT'; i: number` exists precisely for this, `SortEngine.ts:25`). What's missing: (1) no step marks the *lock-in* moment (when the pivot's final swap places it at `i+1`, `:279-283`) as distinct from an ordinary `SWAP` — the pivot's final position is provably permanent the instant `partition` returns (`quickSortRecurse` never touches `pivotIndex` again in either recursive call, `:244-246`), so this is fully knowable at push time. **Gap: reuse the same `FINALIZE` step** (pushed right after the pivot-placing swap at `:283`, for index `i+1`) to mark it, distinguishing it from a routine same-partition swap. (2) No step marks the post-partition split into two independently-active sub-regions — analogous to merge sort's missing region bounds; **same fix as merge sort**, attach `left`/`right` (partition bounds) to `COMPARE`/`SWAP`/`PIVOT` steps emitted inside `partition` (`:254-286`), populated from `partition`'s own parameters.
- **Heap Sort** — not implemented (`SORT_LABELS`/`runSort` in `SortAlgorithms.ts:28-52` covers only bubble/selection/insertion/merge/quick); no gap analysis possible since there is no code to audit. **Unverified / not applicable** — flagged rather than assumed.

**Summary for §2**: every identified gap is a **new field on the runtime-internal `SortStep` union** (`packages/runtime/src/core/algorithms/SortEngine.ts:19-25`) or a **new `SortStep` variant** (`FINALIZE`/`CANDIDATE`), populated inside `SortEngine.ts`'s existing loops where the relevant fact is already in scope. **None of this requires any AQIR/compiler change** — confirmed by §0's finding that builtin sorts are one opaque `GENERIC_ACTION` and everything downstream is a runtime-only concern.

## 3. The narrative layer

### A. On-screen contextual text

**(a) Supported today, data-complete, wrong location only.** The audit already confirms (§7) the `RUNTIME_LOG` text content is correct and complete; the only gap is presentational (rendered in a separate DOM console, `packages/demo/src/components/RuntimeOutputPanel.tsx`, not composited near the canvas). **No AQIR/data-shape change of any kind is implicated** — this is purely a demo-app component-placement decision, out of scope for a backend/AQIR gap document.

### B. Spatial "reason" indicator (connecting line)

**(a) Partially supported at the concept level, not the mechanism level.** A structurally similar concept already exists: `LinkObjectsInstruction{action:'LINK_OBJECTS', sourceId, targetId, directed, relationType?}` (`packages/shared/src/aqir/types.ts:54-60`) compiles from `RelationshipNode` (`generator.ts:1118-1127`), flows into `RelationshipManager`'s `RelationshipEdge{id,sourceId,targetId,type,directed,relationType?}` (`packages/runtime/src/core/RelationshipManager.ts:3-10`), and renders today via `GenericSceneRenderer`'s `type:'edge'` → `PrimitiveEdge` path (per the current-state audit, `GenericSceneRenderer.tsx:40-66,88-98`). This is the closest existing primitive to spec §3B's "connecting line between two elements."
**(b) Gap, precisely.** Three concrete deficiencies, each fixable independently:
  1. **Never emitted by `COMPARE_OBJECTS`/`SWAP_OBJECTS`.** Confirmed: no `LINK_OBJECTS` dispatch or `RelationshipManager` call exists anywhere inside `AnimationController.ts`'s `COMPARE_OBJECTS` (`:427-515`) or `SWAP_OBJECTS` (`:300-425`) handlers, nor in `SortAlgorithms.ts`'s `COMPARE`/`SWAP` step branches (`:108-153`) — confirmed by reading both handlers in full. **Fix: handler-code addition, not a schema change** — both handlers already have `leftEl`/`rightEl` (or `elA`/`elB`) resolved; they can synthesize a `RelationshipManager.addRelationship(...)` call (or an equivalent `LINK_OBJECTS`-shaped ephemeral scene element) using data already on hand.
  2. **`LinkObjectsInstruction`/`RelationshipEdge` has no lifecycle concept — it's designed for permanent structural edges** (e.g. linked-list `next` pointers), not a line that should appear at COMPARE-start and vanish/change at COMPARE-resolution. Neither `LinkObjectsInstruction` (`shared/src/aqir/types.ts:54-60`) nor `RelationshipEdge` (`RelationshipManager.ts:3-10`) has a duration/TTL/transient flag; `RelationshipManager.removeRelationship(id)` exists (`:22-28`) but nothing currently calls it on a timer or animation-complete callback for anything array-related. **Precise fix — new field on the existing `LinkObjectsInstruction`/`RelationshipEdge` shapes**: add `transient?: boolean` and, if the redesign wants scheduler-driven auto-expiry rather than a manual `removeRelationship` call in an animation-complete callback, a `ttlMs?: number`, to both `LinkObjectsInstruction` (`shared/src/aqir/types.ts:54-60`) and `RelationshipEdge` (`RelationshipManager.ts:3-10`). This is a **field addition to an existing instruction/runtime-model pair**, not a new instruction type.
  3. **No color/state field to carry the "comparing vs. resolved vs. decided" grammar the spec asks the line itself to convey** (§3B: "a plain line = comparing, an arrow = moving toward, a broken/snapped line = decision made"). Neither `LinkObjectsInstruction` nor `RelationshipEdge` carries a `color`/`state`/`style` field (contrast with `AQIRObject`, which already has `color?: string`, `shared/src/aqir/types.ts:18` — array/tree/etc. elements can already be colored, edges currently cannot). **Precise fix — new field on `RelationshipEdge` (and, if the redesign wants it compiler-visible for scripted `LINK` statements too, on `LinkObjectsInstruction`)**: add `state?: string` (reusing the existing `SemanticState` union from `packages/shared/src/theme/semanticColors.ts:1-9`, so a comparison-line can be colored `EVALUATING` while pending and re-colored via the same palette once resolved) and/or a `style?: 'solid' | 'arrow' | 'broken'` field for the line-shape grammar itself. Both are **field additions to the existing edge/relationship model**, not new instruction types — the edge-rendering path (`PrimitiveEdge`) already exists and only needs these two fields threaded through to have something to read.

### C. Progress/confirmation marker (sorted vs. unsorted extent)

**(a) Supported today: not at all**, and this is the same underlying gap already flagged in §1.2 and §2. No element-level field exists anywhere for "this position is now permanently confirmed" — `lifecycleState` (`packages/runtime/src/models/SceneElement.ts:18`, values `SPAWNING/ACTIVE/REMOVING/DESTROYED` per `LifecycleManager.ts:9-42`) is about spawn/destroy animation phase, not sort-confirmation; `state`/`highlightType` (set to e.g. `'EVALUATING'` at `AnimationController.ts:440-441`) is transient and gets overwritten by the next operation touching that element — nothing ever sets it to `'SUCCESS'`/sorted-and-permanent for an array element, confirmed by grep: no array-handler code path (`ArrayEngine.ts`, `SortAlgorithms.ts`, `AnimationController.ts`'s `COMPARE_OBJECTS`/`SWAP_OBJECTS`/`GENERIC_ACTION` cases) ever calls `getSemanticColorToken('SUCCESS')` or sets `el.state = 'SUCCESS'`/`'SORTED'` for an array element. (The `SUCCESS` token is used elsewhere only by explicit `HIGHLIGHT ... 'SUCCESS'` script calls, per the current-state audit §6 — an author-driven one-off, not an algorithm-driven persistent marker.)
**(b) Gap, precise fix.** This is exactly the `FINALIZE` `SortStep` addition proposed in §2 (bubble/selection/insertion sort's shrinking/growing boundary, quick sort's pivot lock-in), **consumed by a new persistent-color rule in `SortAlgorithms.ts`'s step-replay loop**: when a `FINALIZE` step for index `i` is encountered, set that element's `state`/color to `SUCCESS`/green **without** the usual settle-back-to-neutral tween every other step type gets (`SortAlgorithms.ts:122,151,206` all currently tween back to `neutralColor` — a `FINALIZE` handler should be the one step type that deliberately does *not* do this, per spec §1.2's explicit note that the confirmed-sorted state is "the one state in the vocabulary that is explicitly persistent"). **Categorization: (i) new `SortStep` variant (`FINALIZE`) in the runtime-internal `SortEngine.ts`/`SortAlgorithms.ts` layer — not AQIR — as established in §2; (ii) no new instruction-level field needed beyond that, since `SceneElement.state`/color already exist and already support a `SUCCESS` token, confirmed above — the gap is purely "nothing ever sets it and holds it," not "no field exists to hold it."**
This section directly enables §2's per-algorithm shrinking/growing/splitting-region signatures, as the excellence spec itself notes (§3C) — the fix is shared, not duplicated, across both.
